# Plan v1 — todo-app

## Problem Statement

The project ships a scaffold that shows one greeting from the API. It has no way to keep a list of tasks. The Developer wants a todo app that stores tasks, removes them and gives each task a due date. The Developer also loves boxer dogs and wants the site to show boxer dog pictures. Today none of that exists.

## Solution

Add a small todo API to the Hono server and a single page to the SvelteKit app. The server keeps todos in memory while it runs. The page lets the Developer add a task, remove it, mark it done and give it a due date. The page shows the task list grouped by due date, and overdue tasks stand out. A boxer dog photo sits at the top of the page and changes when the Developer adds a task. The server fetches the photo from `dog.ceo`, which publishes free dog photos, and falls back to a photo stored in the repository when the fetch fails.

This replaces the single greeting paragraph on the home page.

## User Stories

1. As a **Developer**, I want to type a task and save it, so that I can write down what I need to do.
2. As a **Developer**, I want to remove a task I no longer need, so that my list stays true.
3. As a **Developer**, I want to mark a task done, so that I can see what is finished.
4. As a **Developer**, I want to give a task a due date, so that I know when it is due.
5. As a **Developer**, I want overdue tasks to stand out, so that I notice them without reading every line.
6. As a **Developer**, I want a boxer dog photo on the page, so that the app feels like mine.
7. As a **Developer**, I want a fresh boxer photo when I add a task, so that the page stays fun to use.

## Implementation Decisions

### Modules

**Refactored**

- `web/src/routes/+page.svelte` becomes the todo page. It owns the form, the list and the photo. It calls the API and renders what the API returns.
- `server/src/app.test.ts` and `web/src/routes/page.test.ts` grow cases for the new behaviour.

**New**

- `server/src/todos.ts` holds the in-memory store and the todo rules. It exposes `listTodos()`, `createTodo(input)`, `updateTodo(id, patch)` and `deleteTodo(id)`. It owns id creation, field validation and the "not found" result.
- `web/src/lib/todos.ts` holds the client calls to the API and the shared todo type. The page imports it as `#lib/todos`.
- `web/src/lib/format.ts` holds the due date labels, such as "Overdue", "Due today" and "Due tomorrow".
- `web/static/boxer-fallback.jpg` is the local boxer photo used when `dog.ceo` cannot be reached.

**Extended**

- `server/src/app.ts` gains the `/api/todos` and `/api/boxer` routes. The existing `/health`, `/api/hello` and static file routes stay as they are.
- `deploy/configmap.yaml` and the deployment stay unchanged. The new routes need no configuration.

**Unchanged**

- `web/src/routes/+layout.svelte`, `web/src/app.css`, the build, test and deploy pipelines, and `scripts/smoke.ts`.

### API contracts

All routes send and receive JSON. The server answers an unknown `/api/*` path with a JSON 404, as it does today.

- `GET /api/todos` returns `200` and a list of todos. Each todo has `id`, `title`, `completed`, `dueDate` and `createdAt`. `dueDate` is `"YYYY-MM-DD"` or `null`. `createdAt` is an ISO timestamp.
- `POST /api/todos` takes `title` and an optional `dueDate`. It returns `201` and the new todo. It returns `400` with `{ "error": "..." }` when `title` is empty, longer than 200 characters, or when `dueDate` is not a real `YYYY-MM-DD` date.
- `PATCH /api/todos/:id` takes any of `title`, `completed` or `dueDate`. It returns `200` and the updated todo. It returns `400` for an invalid field and `404` with `{ "error": "Todo not found" }` for an unknown id.
- `DELETE /api/todos/:id` returns `204` when the task existed and `404` with `{ "error": "Todo not found" }` when it did not.
- `GET /api/boxer` returns `200` with `{ "url": "..." }`. It asks `dog.ceo` for a random boxer photo. If that call fails or takes too long, it returns the path of the bundled photo instead. It never returns an error.

The server uses a short timeout for the `dog.ceo` call, so a slow network cannot hold the page. The server does not cache the photo, because a fresh photo per request is the point.

### Data

The server keeps todos in a module-level array for the life of the process. The plan adds no database and no PersistentVolume, because the namespace has none. A restart clears the list. The API shape above is the contract the client relies on, so a later change to real storage keeps the routes the same.

## Testing Decisions

API tests drive the Hono app through `app.request`, as the existing tests do. They cover the full create, list, update and delete cycle. They cover an empty title, a title that is too long, a bad due date and an unknown id. They cover the JSON 404 for an unknown API route.

A test for `GET /api/boxer` stubs the outgoing `dog.ceo` call. It checks the success shape and the fallback when the call fails. The test must not reach the real internet.

Component tests render `+page.svelte` with `fetch` stubbed through `vi.stubGlobal`. They cover the list on first load, adding a task, marking it done, removing it, and the overdue label for a past due date.

`bun run smoke` keeps its current checks. The plan does not extend the smoke script, because the new routes need no new runtime wiring.

## Out of Scope

- User accounts, login and multi-user lists.
- Reminders, notifications and email.
- Editing a task other than its done state, title and due date.
- Search, filters, sorting controls and drag to reorder.
- Persistent storage across restarts.
- Bulk import and export.
- Any change to the Kubernetes manifests.

## Further Notes

- **Chosen:** in-memory storage. No database exists in the namespace, and adding one would widen the change far past the idea.
- **Chosen:** a server-side photo proxy instead of a browser call to `dog.ceo`. The proxy keeps one fetch path, avoids cross-origin problems and gives a place for the fallback.
- **Chosen:** the boxer photo is decorative. The page shows it as an image with empty alt text, because the photo carries no meaning the list needs. The hero heading carries the page meaning.
- **Risk:** `dog.ceo` may be unreachable from the cluster. The bundled fallback photo covers that case, so the theme still works.
- **Risk:** an in-memory list loses tasks on every deploy or restart. The plan accepts this for now. A later Plan can add storage without changing the API.
